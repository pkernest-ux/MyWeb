# V4 視覺定向（近似）

版本說明：民眾端已加入新的[連續相機導引](./ar-v4-continuous-guidance.md)。照片取得初始方向後，改由感測器與步伐延續近似路徑；以下 15 秒有效期描述的是影像方向證據／工作台診斷，不再是民眾端路線顯示的唯一開關。

視覺定向把「相機畫面中央」對應到已校正的環景方向，再以手機轉動維持短時間的箭頭方向。它不是手機 XYZ 座標、精確姿態、測距或已抵達證明；也不代表完成現場精度驗收。

## 使用前提

- 既有環景若具有批次、yaw／pitch／視角與已確認的地圖方向，不需要重新上傳，使用已發布的 Fishnet 特徵包即可；尚無 Fishnet 包才需要發布特徵包。缺少這些資料的舊照仍可辨識節點，但不能自動定向。
- 先確認環景的 0° 與地圖方向關係。地圖上方是 0°，不是自動取得地磁北方；未校正的環景不能靠辨識補出正確地圖朝向。
- 請停在原環景拍攝位置附近、對準固定地標。相同節點在 8 秒內取得 3 次一致且有效的視覺量測後，才顯示「視覺定向（近似）」。三次取樣不等於三個獨立現場位置的驗證。
- 只有目前已確認所在節點的參考資料可自動定向；附近或下一地標即使可辨識，也不能假設手機已站在其拍攝位置。下一節點須人工確認抵達後，才能作為新的自動定向依據。
- 仍須允許方向感測，才能融合手機轉動。沒有可用感測、資料不足、量測矛盾或超過 15 秒沒有有效更新時，回到等待／重新確認狀態；可用人工校正與地圖。
- 看見下一地標不會自動更新位置；實際走到後仍要按「我已到達」。
- 工作台匯入測試照只顯示「單張照片試算」，不拿現在手機的感測資料替舊照片校正方向，也不會要求開啟相機。

## 為什麼不是直接使用照片方向

照片的中心方向不一定等於使用者目前畫面的中心方向。實作從已驗證的配對點估算影像間的投影關係，反推當前畫面中央落在參考環景的哪裡，再取得近似方向。移動到不同拍攝位置、強烈視差、重複紋理與錯誤環景校正都可能破壞這項近似。

平面投影關係適合平面景物，或繞同一投影中心旋轉的相機；不能直接當作任意室內移動的完整定位。[OpenCV 官方 homography 教學](https://docs.opencv.org/4.13.0/d9/dab/tutorial_homography.html)

手機的 `alpha` 或螢幕上緣方向也不總是後相機看向的方向。方向追蹤使用旋轉後的背面光軸（−Z）水平投影，並在手機近乎朝天／朝地、投影不可靠時拒絕定向；螢幕橫直向不是再加一個 90° 的相機朝向。[W3C Device Orientation 模型與 AR 方向範例](https://www.w3.org/TR/orientation-event/#a-1-calculating-compass-heading)

## 本機回歸測試

先以本次來源重建 V4 field／navigation，再執行：

```sh
node test/ar-v4-heading-browser.mjs
```

測試沿用已安裝的 Playwright／Chrome，可用 `AR_V4_TEST_PLAYWRIGHT` 與 `AR_V4_TEST_CHROME` 指定路徑。只用合成圖與獨立暫存資料，不使用真實現場照片，不上傳資料，不修改既有後台或 V3。報告與截圖位於 `test-output/visual-heading/`。

主要檢查：第 1／2 次不定向、第 3 次才定向；偏心裁切圖的光軸不能冒用照片中心方向；失去視覺時保留短期轉動；不自動抵達；舊照人工退路；方向權限缺失；390／1280 畫面無橫向溢出；民眾端僅載入特徵包。

2026-09-07 本機回歸：7 項通過，6 張兩尺寸截圖已目視檢查。首個相機影格可能早於第一筆可用感測資料，該影格即使辨識成功也不計票；其後有效量測依序為 1／2 次待確認、3 次定向。合成偏心裁切估算 98.2°（獨立幾何預期約 98.187°，參考照中心 90°），空白畫面下模擬轉動 40° 保留了 40° 箭頭變化。工作台單張匯出確認 `heading.still=true`、`heading.sensor=null`，沒有請求相機或感測權限。這些數值只證明已知合成條件的計算與整合，不是現場誤差統計。

這些是桌面瀏覽器的模擬回歸，不是 iPhone／Android／LINE 實機、相機內參、磁場品質或現場定位成功率保證。本文件也不表示任何版本已推送或部署。
